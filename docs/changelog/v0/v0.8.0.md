# gh-broker v0.8.0 Changelog

**Release Date**: October 2026
**Release Type**: Minor
**Branch**: `release/0.8.0`

---

## Overview

v0.8.0 adds two write integrations that let an agent do work which used to need a token in its own hands or a human at a web form. `npm_scaffold` creates a new npm package and registers its trusted publisher, so the repo's CI can publish the first real release through OIDC. `ghcr_push` pushes a `docker save` archive to the GitHub Container Registry with a credential the agent never sees, with `ghcr_push_status` and `ghcr_tags` to follow the job and check the result.

Both are optional. Their credentials (an npm granular token and a classic `write:packages` PAT) can be skipped at install, and while one isn't stored the broker starts normally and leaves the matching tools out of the tool list. The installer also gains a `--secret <cred-name>=<token>` flag, and supplying a token explicitly now replaces the stored one on the `file` backend as well.

Owner-specific settings no longer ship in `config.example.json`: the installer takes them from `--config <file>` or a flag per setting, and an existing install keeps what it has.

Nothing is breaking. Every existing verb and proxied tool behaves as in v0.7.0. The only runtime dependency change is `@modelcontextprotocol/sdk` 1.32.1 → 1.32.2.

## ✨ Features

### `npm_scaffold`: create an npm package and its trusted publisher ([#127](https://github.com/CLDMV/gh-broker/pull/127))

npm only accepts a trusted publisher on a package that already exists, so every new package needed a hand-run first publish and a form on npmjs.com. `npm_scaffold` (`mode: "write"`, `custom: true`) does both.

- **Placeholder publish.** The broker builds a tarball itself (a `package.json` at `0.0.0-stage` marked `scaffoldedBy: "gh-broker"`, and a README pointing at the repo) and publishes it. Access is `public` for a public repo and `restricted` for a private one.
- **Trusted publisher.** It then registers the repo's publish workflow (default `publish.yml`) as the package's GitHub Actions trusted publisher, the same request `npm trust github` sends.
- **One OTP per write.** The broker's npm token has no 2FA bypass, so each npm write carries a one-time password from the user. The first call publishes and returns `status: "needs_otp"` with the trust step remaining; a second call with the next code adds the trusted publisher. A refused or expired code also returns `needs_otp` with what is left.
- **Create-only.** The scope must be in `config.npm.scopes`. The repo must exist under exactly the owner and name given (a redirect from a rename or transfer is refused), must not be archived, and its `package.json` on the default branch must name this package and not be private. The publish workflow must exist. A package already on the registry is refused, unless it is this verb's own placeholder for the same repo, which is how an interrupted call resumes. The lookup reads the registry primary (`?write=true`), not a cache.
- **Existing trust.** If npm answers that a trusted publisher already exists (HTTP 409), the configuration is read back: the same repo and workflow counts as done, anything else fails naming what is configured.
- **No secrets out.** Neither the OTP nor the token appears in a result, an error or the audit log.

Installer support: `--npm` runs an npm web login, asks for the npm password and an OTP (both hidden, the password is never stored), and creates a granular token for the chosen scopes (`--npm-scope`, repeatable) with `--npm-token-days` lifetime (default 90). `--npm-org` (repeatable) also grants org read-write and is saved as `npm.tokenOrgs` so a rotation creates the same kind of token. Unattended installs take an existing token from `--secrets-file` or `GH_BROKER_SECRET_NPM_TOKEN`. Rotating says plainly that the old token stays valid until it expires or is revoked.

Full reference: [docs/TOOLS.md](https://github.com/CLDMV/gh-broker/blob/master/docs/TOOLS.md#npm_scaffold) and [deploy/README.md](https://github.com/CLDMV/gh-broker/blob/master/deploy/README.md#npm-integration-npm_scaffold).

### `ghcr_push`, `ghcr_push_status` and `ghcr_tags`: GHCR pushes without an agent-held token ([#128](https://github.com/CLDMV/gh-broker/pull/128))

`ghcr_push` pushes an image archive to `ghcr.io/<owner>/<image>:<tag>` using the owner's GHCR credential from the new `config.ghcr` block, a classic PAT with `write:packages` (GHCR does not accept fine-grained PATs).

- **Archives.** Both `docker save` formats are read: the OCI image layout from Docker 25+ (also `buildx --output type=oci`) and the older docker-archive. An archive must hold exactly one single-platform image; attestation manifests are ignored. Compressed layers are pushed byte-for-byte, uncompressed layers are gzipped while they upload.
- **Push flow.** The OCI distribution API from Node, with no docker socket and no extra binaries. Blobs the registry already has are skipped, so re-pushing an unchanged image uploads nothing. Nothing is buffered in memory or written to disk.
- **Background jobs.** The call validates, exchanges the PAT for a registry token, checks tag protection and returns a job id at once. Jobs run one at a time, at most 8 queued or running. `ghcr_push_status` reports the phase, blob counts and bytes, then the manifest digest or the error. Job state is in memory only; a push cut off by a restart leaves nothing tagged.
- **`ghcr_tags`** lists an allowlisted image's tags with a pull-only token, to check that a push landed.
- **Guardrails, all before any upload.** The image must match the owner's `images` allowlist (`*` stays within one path segment). The archive must sit inside `ghcr.dropDir`: the path is checked as text, the file is opened once with `O_NOFOLLOW`, and the open descriptor must be a regular file with a single link whose real path is inside the real drop directory, so a symlink, hard link or symlinked subdirectory can't point the broker at a file the agent can't read. With `protectReleaseTags` (default on), an existing `1.2.3` / `v1.2.3` tag is never overwritten, checked at submit and again before the manifest is written.
- **Credential containment.** The PAT is only sent to `https://ghcr.io/token`, the registry token only to `https://ghcr.io`, redirects are never followed, and every error passes through a scrubber before it reaches a result, audit line or log.

GHCR is set up per install with `--ghcr-owner`, `--ghcr-username` and `--ghcr-image` (or a `--config` file), and the credential is `<org>-packages`. The installer creates the drop directory as `2750 <agent-user>:gh-broker`.

Full reference and threat model: [docs/TOOLS.md](https://github.com/CLDMV/gh-broker/blob/master/docs/TOOLS.md#ghcr_push) and [deploy/README.md](https://github.com/CLDMV/gh-broker/blob/master/deploy/README.md#configuring-the-install).

### Optional credentials hide their tools instead of blocking startup ([#127](https://github.com/CLDMV/gh-broker/pull/127), [#128](https://github.com/CLDMV/gh-broker/pull/128))

The npm token and the GHCR credentials are optional. The installer lets them be skipped (Enter at the prompt; an unattended run skips with a note), and only stored credentials go into the systemd drop-in. At startup the broker leaves a tool whose credential isn't stored out of the tool list, refuses a call to it like an unlisted tool, and logs why. Only the owners' GitHub PATs are required.

### Generic shipped config: `--config` and a flag per setting ([#135](https://github.com/CLDMV/gh-broker/pull/135))

`config.example.json` now ships only the generic defaults: the socket, the upstream and the tools allowlist. It used to carry this project's own owner, GHCR account and image list, and the installer forced them onto every install, so anyone installing the package was asked for `cldmv-read`, `cldmv-write` and `cldmv-packages`.

Owner-specific settings now come from the operator, layered from lowest to highest precedence: the shipped defaults, the deployed config, a `--config <file>`, then the CLI flags. There is a flag for every setting: `--owner <org>` (repeatable, credentials `<org>-read` / `<org>-write`), `--default-owner`, `--listen`, `--upstream`, `--installation-id`, `--app-id`, `--app-private-key`, `--secrets-path`, `--npm-registry`, and for GHCR `--ghcr-owner`, `--ghcr-username`, `--ghcr-image`, `--ghcr-drop-dir`, `--ghcr-max-archive-bytes` and `--[no-]protect-release-tags`.

- The tools allowlist still always comes from the repo. A `--config` file that sets `tools`, has an unknown top-level key or holds anything shaped like a token is refused.
- A first interactive install asks for the owner; an unattended one with no owner fails and names `--owner` / `--config`.
- An upgrade without config flags keeps the deployed owners and GHCR settings as they are.
- `config.sample.json` shows a full config with placeholder values. Nothing loads it.

Full reference: [deploy/README.md](https://github.com/CLDMV/gh-broker/blob/master/deploy/README.md#configuring-the-install).

### Installer: `--secret <cred-name>=<token>` ([#127](https://github.com/CLDMV/gh-broker/pull/127))

A fourth way to supply a token, repeatable, taking precedence over `--secrets-file`, `GH_BROKER_SECRET_<NAME>` and the prompt. A name the config doesn't use is refused, so a typo can't silently do nothing. It shows up in the process list and shell history, so the file or env are still the better choice for real tokens.

## 🐛 Bug Fixes

### The `file` secrets backend ignored a newly supplied token ([#127](https://github.com/CLDMV/gh-broker/pull/127))

When a token was passed through `--secrets-file` or env for a credential that was already stored, the `file` backend kept the old value. It now replaces it, which is what `systemd-creds` already did and what the docs described.

## Upgrade notes

- A fresh unattended install now needs `--owner <org>` (or a `--config` file with an `owners` block); it used to pick up the owner shipped in `config.example.json`. Upgrades are not affected.
- No breaking changes. Without an `npm` block or a stored GHCR credential, the broker behaves exactly as v0.7.0 and the new tools are not exposed.
- Re-run the installer to deploy: it merges the new allowlist entries into the live config, rebuilds and restarts. Existing owners and settings are kept. MCP clients need to reconnect to see new tools.
- To enable `npm_scaffold`, run the installer with `--npm` (add `--npm-org <org>` if creating packages in the scope needs org permissions).
- To enable `ghcr_push`, create a classic PAT with `write:packages` only ([create the token](https://github.com/settings/tokens/new?scopes=write:packages&description=gh-broker%20ghcr)), and run the installer with `--ghcr-owner <org> --ghcr-username <login> --ghcr-image <name>` (repeat `--ghcr-image` per image). It asks for the token as `<org>-packages`, or takes it from `--secret <org>-packages=<token>`.
