# gh-broker v0.11.1 Changelog

**Release Date**: November 2026
**Release Type**: Patch
**Branch**: `release/0.11.1`

---

## Overview

v0.11.1 fixes v0.11.0, whose daemon crashed at startup, so `sudo gh-broker install` failed and never deployed it. Everything v0.11.0 added, including `npm_scaffold`'s `path` and `ref`, works as described in the [v0.11.0 changelog](./v0.11.0.md).

---

## 🐛 Bug Fixes

### The daemon bundle loads again (fixes [#208](https://github.com/CLDMV/gh-broker/issues/208))

v0.11.0 started importing `@cldmv/lib-otp`, whose main entry loaded `qrcode` for QR rendering. The daemon bundles every dependency into one ES module, so `qrcode` (CommonJS) came along, and its `require("fs")` threw `Dynamic require of "fs" is not supported` at load. `gh-broker install` runs the daemon (`--print-paths`) before deploying, so it stopped there and the service kept running v0.10.7.

`@cldmv/lib-otp` 0.2.0 moves `renderQr` to its own `@cldmv/lib-otp/qr` subpath. The daemon imports only the main entry, and only the `gh-broker` command imports the QR renderer, so the daemon bundle no longer contains `qrcode` at all. gh-broker no longer depends on `qrcode` directly.

---

## 🔧 CI & tooling

- `npm run build` now runs the built daemon (`dist/index.mjs --print-paths`) from a copy with no `node_modules`, the way `/opt/gh-broker` runs it, plus `bin/gh-broker.mjs --help`. It also fails if the daemon bundle still holds a dynamic `require()`. CI and `npm publish` both build, so a bundle that can't load can't ship. Every unit test runs against `src/`, which is why v0.11.0's broken bundle passed CI.

## Upgrade notes

- No breaking changes. Upgrade with `sudo npm install -g --prefix /usr/local --ignore-scripts @cldmv/gh-broker@latest`, then `sudo gh-broker install`. If v0.11.0's install failed for you, this is the fix; `/opt/gh-broker/version` should read `0.11.1` afterwards.
